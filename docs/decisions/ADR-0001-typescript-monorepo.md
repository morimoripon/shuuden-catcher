# ADR-0001: TypeScript のモノレポで構成し、API は Next.js から分ける

- **Status**: Accepted
- **Date**: 2026-10-07
- **関連**: ADR-0002（API が時刻表を読み込む元）

## 背景（Context）

終電キャッチャーは次の 4 つで構成する。

- モバイルアプリ: 駅登録、「今日だけ ON」、ローカル通知
- Web: LP と、アプリを入れなくても試せるデモ
- API: 終電の計算と駅検索
- batch: ODPT の時刻表を取り込み、前処理する

終電の計算はサーバー側で行う。端末は「今日だけ ON」にした時点で API を 1 回呼び、結果からローカル通知を予約する。

制約は次のとおり。ソロ開発で、目的は収益ではなく GitHub で公開するポートフォリオ。運用費はできるだけ掛けない。
clone した人が API キーなしで動かせるサンプルデータのモードも用意したい。

## 決定（Decision）

pnpm + Turborepo の TypeScript モノレポにする。

```
apps/
  mobile/   Expo (React Native)
  web/      Next.js
  api/      Hono (Node)
  batch/    ODPT 取り込みジョブ
packages/
  core/     終電計算アルゴリズム（逆向き RAPTOR / CSA）
  schema/   zod の型定義（API 入出力）
  api-client/
```

1. **終電計算は `packages/core` に置き、api と web デモの両方から使う。** web デモはサンプルデータならブラウザの中で core を動かし、サーバーを使わずに終電を計算する
2. **API は Next.js の Route Handlers に相乗りさせず、Hono の独立したサーバーにする。** 時刻表をメモリに載せて計算するため、Cloud Run / Fly.io のような常駐できる場所に置く
3. **API の入出力は `packages/schema` の zod で定義する。** api・api-client・mobile が同じ型を使う

## 代替案（Alternatives）

- **API と core だけ Go で書く**: 大きな時刻表をメモリに載せたときの速度とメモリ効率は Go の方が有利。ただ、core を Go で書くとブラウザで動かせなくなり、web デモにサーバーが要る。型も OpenAPI を経由して生成することになり、1 人で 2 言語のツールチェーンを保守することになる。今の規模では Node で足りる見込みなので却下。
- **API を Next.js の Route Handlers に置く**: デプロイ先が 1 つで済む。ただ、サーバーレス関数では呼び出しのたびに時刻表を読み直すおそれがあり、メモリの上限にもかかりやすい。時刻表をメモリに常駐させたい API とは合わないので却下。
- **API を置かず、batch で終電表を事前計算して静的に配信する**: 逆向き探索は目的駅から 1 回走らせると、全駅からの終電がまとめて出る。batch で「自宅駅ごとの終電表」を作って静的に配信すれば、API を常駐させなくて済む。構成はいちばん軽いが、API の設計や実装を見せる部分が無くなり、ポートフォリオの目的に合わないので採らない。運用費が問題になったときの移行先として残す。

## 結果・影響（Consequences）

- 全体を TypeScript 1 言語で書け、型と終電計算のロジックをアプリ間で共有できる
- web デモは、サーバーも API キーも無しで動かせる
- 時刻表の載せ方によっては Node のメモリ効率が足りなくなるおそれがある。core の検証で首都圏のデータを載せ、メモリ量を測って確かめる
- API はスケールゼロからの起動時に時刻表を読み込むため、最初のリクエストが遅くなる。前処理後のデータ形式を小さくまとめて抑える
- 見直し条件: 首都圏のデータを載せた API が、Cloud Run / Fly.io の無料枠や低額プランのメモリに収まらない場合。そのときは本 ADR を Superseded にし、Go への置き換えか事前計算への移行を新規 ADR で判断する
