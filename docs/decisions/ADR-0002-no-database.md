# ADR-0002: DB を持たず、時刻表と駅マスタはオブジェクトストレージからメモリへ読み込む

- **Status**: Accepted
- **Date**: 2026-10-07
- **関連**: ADR-0001（API が時刻表をメモリに載せる前提）

## 背景（Context）

当初は PostgreSQL + PostGIS を置き、駅マスタと「現在地からの最寄駅検索」を DB に持たせる案だった。

しかし、サーバー側で保存が必要なデータはほとんど無い。

- 登録駅や「今日だけ ON」の状態は端末に保存する。ユーザーアカウントは作らない
- 時刻表は、終電の計算のために API がメモリへ載せる（ADR-0001）
- 残るのは駅マスタだけで、首都圏の ODPT 対応路線なら数千行に収まる

また、時刻表は ODPT の利用規約上再配布できない可能性があるため、リポジトリにはコミットしない。

制約は次のとおり。ソロ開発のポートフォリオで収益は無く、運用費はできるだけ掛けない。

## 決定（Decision）

DB は持たない。

1. **batch が前処理した時刻表と駅マスタを、非公開のオブジェクトストレージに置く。** GCS / R2 のどちらにするかは未定
2. **API は起動時にそれをメモリへ読み込む。** 終電の計算も最寄駅の検索もメモリ上で行う
3. **API のテストは、小さなフィクスチャの時刻表をメモリに載せて行う。**

## 代替案（Alternatives）

- **PostgreSQL + PostGIS**: 最寄駅検索を SQL で書けて、DB の設計を見せられる。ただ、駅マスタ数千行のために DB を常時動かすことになり、マネージド DB の費用か、Neon などの無料枠の制約がかかる。テストにも testcontainers が要る。数千件の最寄駅検索はメモリ上の線形探索でも足りるので却下。

## 結果・影響（Consequences）

- DB の運用費と、マイグレーション・testcontainers の手間が無くなる
- ローカルでも CI でも、API はファイルを読むだけで起動できる
- DB を扱える部分はこのリポジトリでは見せられない
- 時刻表を更新するには、batch のあとに API を再起動して読み込み直す必要がある
- 見直し条件: ユーザーアカウントや端末間の同期など、サーバー側に保存するデータが出てきた場合。そのときは本 ADR を Superseded にし、DB の採用を新規 ADR で判断する
