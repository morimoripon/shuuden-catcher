# アーキテクチャ決定記録（ADR）

終電キャッチャーの「巻き戻しにコストがかかる判断」について、**理由・代替案・結果**を記録する。
PR 本文やコミットメッセージに散在しがちな「なぜこう決めたか」を一箇所に集約し、将来の再導出コストを下げるのが目的。

## いつ ADR を書くか

以下に該当する変更は ADR の追加を必須とする:

- アーキテクチャの確定判断（採用スタック・データの持ち方・経路データの取得元など）を決める・覆すとき
- 外部サービスやデータの利用条件（ODPT の利用規約など）によって設計を変えるとき

軽微な実装変更・バグ修正・リファクタリングには不要。

### 迷ったときの判断

一つの問いに集約する。

> **数ヶ月後の自分が「なぜこの選択をしたのか」を知る必要があるか。**

必要なら ADR。不要なら不要。実装が正しいかどうかとは別の問いで、
「はい」なら選択の背景・却下した選択肢・トレードオフが、放っておくと失われる情報になる。

補助的な手掛かり（当てはまるほど ADR 向き）:

- 検討して**却下した選択肢**があり、その理由が実装コードからは読み取れない
- ソロ開発・収益なし（運用費を掛けない）・API キーなしで動かせることといった**外部制約**が判断を左右した
- 「なぜ普通のやり方をしていないのか」と後から聞かれそうな形になった
- 一度決めたら**巻き戻しにコストがかかる**（データの持ち方・API の境界・配信方式）

### 誰が起票するか

Claude は、会話や設計の流れの中で重要な判断が固まったら
**「これは ADR にしますか？」と能動的に確認する**。実装者が思い出して依頼するのを待たない。
ただし黙って作成はしない。必ず確認を挟む。

## 運用ルール

- ファイル名は `ADR-XXXX-<短い英小文字スラッグ>.md`（連番・ゼロ埋め 4 桁）。
- 一度 `Accepted` になった ADR は**書き換えない**。方針が変わったら新しい ADR を起こし、旧 ADR の Status を `Superseded by ADR-YYYY` に更新する。

## テンプレート

```markdown
# ADR-XXXX: <タイトル>

- **Status**: Proposed | Accepted | Superseded by ADR-YYYY
- **Date**: YYYY-MM-DD
- **関連**: PR #NNN / 関連 ADR

## 背景（Context）
何が問題で、どんな制約（ソロ開発・収益なし・API キーなしで動かす等）の下で判断したか。

## 決定（Decision）
何を採用したか。断定形で書く。

## 代替案（Alternatives）
検討して採用しなかった選択肢と、却下した理由。

## 結果・影響（Consequences）
この決定によって得たもの・引き受けたトレードオフ・将来の見直し条件。
```
